\section{Check 3: Live Gateway}\label{sec:live}

\emph{What an offline score hides.} A gateway classifies flows exported while packets still arrive, not flows from a finished file. Equal scores do not show that both see the same flows, so we check fidelity flow by flow.

\subsection{Testbed}\label{sec:testbed}

The testbed runs Mininet~2.3.0~\cite{lantz2010mininet} with Open vSwitch~\cite{pfaff2015ovs} under WSL2 Ubuntu~24.04 on a laptop (i5-8350U, no GPU). In the topology h1--s1--gw--s2--h2, h1 replays traffic with tcpreplay at $\times1.0$ timing, and the gateway gw captures on its s1-facing interface. The gateway runs NFStream~6.6.0 in live mode with the offline settings, a single meter and a 64\,MB capture buffer. Exported flows are classified in micro-batches (256 flows or 50\,ms) by the deployed tree; each flow receives one \emph{verdict}, its predicted class.

\emph{Windows and harness.} For each capture we cut one 60\,s window that starts 1\,s after the last training flow started, so all replayed traffic comes from the test period. Boundary-spanning connections are removed on both the offline and the live side; the offline reference is NFStream run on the same window file. After each window the harness waits until the gateway is idle and clears OVS blocks, per-pair verdict counts and ARP state, since the sessions reuse addresses. The first no-limit run (run~1) and the one-core run used an earlier harness without the quiet wait and the reset. A cgroup quota (\texttt{systemd-run}) sets the gateway's CPU budget: no limit, one core or half a core.

\emph{Achieved replay rates.} tcpreplay could not reach the original rate of the heaviest windows: DDoS-SYN (17,424 packets per second, pps) and Mirai (4,782\,pps) were replayed at 46--81\% of it.

\subsection{Fidelity Check}\label{sec:fidelity}

\emph{Flow-by-flow match.} We match live to offline flows by 5-tuple and order of appearance within the 5-tuple, on every run. In each of the sixteen repeat and CPU-budget runs without enforcement, at least 99.98\% of the offline flows match a live flow and at least 99.97\% of the matched flows receive the same verdict. Macro-F1 over run~1's windows (not comparable to the test-set score) is 0.804 both offline and live.

\emph{Packets and delay.} Live and offline flows hold the same packets to within 1\% in every window, with zero kernel drops. Inference takes under half a millisecond per batch of about 200 flows. Delay comes from flow export, as expected for flow-based detection~\cite{hofstede2013realtime}: the median verdict arrives about 15\,s (the idle timeout) after a flow's last packet, and the first verdict for an attacker pair 15--35\,s after its first packet.

\emph{Repeats: macro-F1 hides flow splitting.} We ran the no-limit and half-core settings three times each and the one-core setting once (Table~\ref{tab:repeats}). Every run captured every packet, but flow construction followed the replay rate. At 69\% or more of the original DDoS-SYN rate the live flow count matched offline; in the slower runs it was up to 29\% higher, and fewer matched flows had identical packet counts, because slower replay stretches inter-packet gaps past the idle timeout and splits connections. Macro-F1 did not move. This is Check~3 applied to our own runs: only the flow-by-flow match shows the loss of fidelity. It matters downstream, because a rule that counts verdicts per host pair counts the pieces of a split flow separately (Section~\ref{sec:response}).

\emph{CPU budget, without the confounds.} Table~\ref{tab:repeats} confounds the budget with replay rate (tcpreplay shared the CPU), harness version and window set, so we ran the three windows nine more times with one harness, budgets interleaved, and tcpreplay, ping and gateway pinned to disjoint cores. Only the DDoS-SYN window responded: its median delay was about 18\,s with no limit, 22--38\,s with one core and 39--89\,s with half a core, with no overlap between budgets (exact Kruskal--Wallis permutation $p=0.004$). Controlling for the replay rate, half a core adds about 43\,s; the one-core effect is not significant. Pinning did not fix the DDoS-SYN replay rate, slower replay went with longer delay, and the one pinned run below 69\% of the original rate split flows again. With half a core the gateway needed up to three minutes to clear its backlog, but no run dropped a packet: CPU pressure caused lag, not loss, for floods that did not fill the 64\,MB buffer. Peak memory stayed near 1\,GB (NFStream and Python, not the tree).

\subsection{Failure Modes the Check Exposed}\label{sec:defect}

The fidelity numbers above hold only after three problems were fixed. None changed an offline score, since at end of file every remaining flow is flushed.

\emph{A forwarding pitfall.} Replayed frames carry the source MACs of many capture devices. A MAC-learning switch maps all of them to h1's port and never forwards frames addressed to them, so part of the traffic silently never reaches the detector. Packet accounting reveals this; one OVS rule that forwards everything from h1 to gw fixes it.

\emph{Idle meters.} NFStream checks a meter's timeouts only when that meter receives a packet, so idle flows can wait in a meter that receives none. We use one meter and run a 200\,pps keep-alive ping between h1 and h2 on a management subnet that is never scored or blocked.

\emph{An export-ordering defect.} Unpatched NFStream~6.6.0 delivered verdicts tens of seconds after the idle timeout. \texttt{NFCache}, a least-recently-used (LRU) \texttt{OrderedDict}, moves a key to the most-recently-used end only in \texttt{\_\_setitem\_\_}, but \texttt{consume()} updates an existing flow in place, so the cache stays in creation order. \texttt{meter\_scan()} expires flows from the head and stops at the first non-idle flow. One long-lived active flow, such as the keep-alive ping, therefore blocks the idle expiry of every flow behind it until its 120\,s active timeout. A one-line fix, \texttt{cache.move\_to\_end(flow\_key)} in the update branch, restores LRU order without changing flow boundaries or features, so offline comparisons cannot see the defect. It cut the median delay after flow end from 82.5\,s to 15.6\,s in the SQLi window and from 49.2\,s to 15.5\,s in the XSS window. In the unpatched XSS run about a third of the packets were still in unexported flows when the run stopped; on a continuously running gateway they would be exported late, not lost. Pekar and Jozsa leave ``the specific mechanisms employed for updating and terminating flows'' out of scope~\cite{pekar2024integrity}. Late idle export has another, already diagnosed cause: a capture loop that blocks while no packet arrives, so expiry never runs (nfstream\#215, 2024~\cite{nfstream215}). Our keep-alive ping rules that cause out, and to our knowledge the LRU-ordering cause was previously undiagnosed. Any exporter whose expiry path differs from its end-of-file flush can hide such defects from offline evaluation. We reported it as nfstream\#262~\cite{nfstream262} and submitted the fix with a regression test as PR~\#263~\cite{nfstream263}.\footnote{The symptom was also reported without a cause in nfstream\#106 (2022)~\cite{nfstream106}, \#120 (2022)~\cite{nfstream120} and \#193 (2024)~\cite{nfstream193}.}
